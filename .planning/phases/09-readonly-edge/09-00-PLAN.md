# Phase 9: Read-Only Immutable Engine

**Status:** Planned | **Target Milestone:** v1.2

**Goal:** Enable EdgeStore to serve reads in environments with no local filesystem, no persistent writer process, and no locking — specifically serverless functions, edge runtimes, and WASM. Build an `ImmutableEngine` that reads content-addressed segments directly from object storage into memory, with zero WAL, zero memtable, and zero write amplification.

**Requirements:** RO-01 through RO-08

---

## Background and Motivation

EdgeStore's single-writer design is its superpower for SSD durability and crash safety. But it is also the primary blocker for adoption in serverless environments:

| Environment | Has local disk? | Has persistent process? | Can lock files? |
|-------------|-----------------|----------------------|-----------------|
| Traditional server / VM | Yes | Yes | Yes |
| Docker container | Yes (ephemeral) | Yes | Yes |
| Kubernetes pod | Yes (ephemeral) | Yes | Yes |
| **Serverless / edge runtime** | **No** | **No** | **No** |
| **WASM browser runtime** | **No** | **No** | **No** |

Users in these environments want to **query** EdgeStore data (GET, RANGE, PREFIX, VECTOR_SEARCH, TEXT_SEARCH) without writing, compacting, or maintaining a local database. They want to treat object storage as a read-only segment store.

The current `TieredEngine` is close but wrong for this use case:
- It wraps `Engine`, which requires a `db_path`, `LOCK` file, WAL, and memtable
- `fetch_and_import()` pumps downloaded segments through WAL → memtable → `SegmentStore` — write amplification on a read path
- It has no "manifest as single object" concept; segment discovery uses `ListObjectsV2` or equivalent

`ImmutableEngine` is the clean-slate solution.

## Architecture

### ImmutableEngine

```rust
pub struct ImmutableEngine {
    /// All segments visible to this engine, in LSN order (newest first for get()).
    readers: Vec<InMemorySegmentReader>,
    /// Content-addressed cache of raw .dat bytes, keyed by BLAKE3 hash.
    /// Optional: if not provided, segments are re-downloaded on every init.
    segment_cache: Option<lru::LruCache<[u8; 32], Arc<Vec<u8>>>>,
    /// Remote store for lazy fetching.
    remote: Option<Box<dyn RemoteStore>>,
    /// Segment metadata for lazy fetching (hash → bounds mapping).
    remote_segments: Vec<ArchivedSegment>,
}
```

### InMemorySegmentReader

- `.dat` bytes in memory (`Arc<Vec<u8>>` or `bytes::Bytes`)

### Manifest Format (Single JSON Object)

Stored in object storage as `{bucket}/{prefix}manifest.json`:

```json
{
  "version": 1,
  "created_at": 1751692800000000000,
  "segments": [
    {
      "hash": "a1b2c3...",
      "min_key": "...",
      "max_key": "...",
      "min_lsn": 1000,
      "max_lsn": 1500,
      "record_count": 50000,
      "sidecars": true
    }
  ]
}
```

**Why one object instead of ListObjectsV2?**
- `ListObjectsV2` (or equivalent) is a paginated scan. For 10K segments, it can take 100+ API calls.
- One `GetObject` on a 50 KB manifest is ~$0.0000004. One list page is ~$0.000005. At scale, the manifest is 10× cheaper and 100× faster.
- The manifest can be cached by CDN or runtime cache. Listing APIs typically cannot be cached (dynamic scans).
- The manifest is updated atomically by the writer on every flush/archive cycle.

### Two Modes: Eager vs. Lazy

| Mode | Init Time | Memory | First Query Latency | Use Case |
|------|-----------|--------|---------------------|----------|
| **Eager** | Downloads all segments at init | High (all segments in RAM) | Zero (all local) | Small datasets (<1GB), warm cache |
| **Lazy** | Downloads manifest only | Low (empty) | Remote round-trip for first access to each segment | Large datasets, memory-constrained environments |
| **Hybrid** | Downloads manifest + hot segments (configurable) | Medium | Zero for hot, remote for cold | Time-series: recent segments hot, old segments cold |

The default for serverless should be **Lazy**. The writer can tag segments as "hot" in the manifest (e.g. `cohort_bucket >= now - 24h`).

## Implementation Plan

### Wave 1: Core In-Memory Segment Reader

**File:** `edgestore/src/segment/in_memory.rs`

1. `InMemorySegmentReader::from_bytes()` — parse `.dat` file from memory buffer
   - Parse file header (magic + version)
   - Iterate blocks: read magic, compressed_len, decompress ZSTD, parse records
   - Build sparse index: store `(encoded_key, block_offset)` every N keys
   - Build xor filter from all keys
   - Store in struct

2. `InMemorySegmentReader::get()` — point lookup
   - xor filter fast-reject
   - sparse index binary search → block offset
   - decompress block, scan for key
   - Return `Option<MemEntry>`

3. `InMemorySegmentReader::range_scan()` — range query
   - Use sparse index to find starting block
   - Decompress blocks, collect records in range
   - Return `Vec<(Vec<u8>, MemEntry)>`

**Tests:**
- Roundtrip: write a segment with `SegmentWriter`, read it with `InMemorySegmentReader`
- Point lookup: present key, absent key (xor filter reject)
- Range scan: inclusive start, exclusive end, sorted output
- Large segment: 100K records, verify performance <10ms per get

### Wave 2: ImmutableEngine

**File:** `edgestore/src/immutable.rs` (or new crate `edgestore-immutable`)

1. `ImmutableEngine::from_manifest_bytes(manifest_json: &[u8])`
   - Parse manifest JSON
   - For each segment entry, create a placeholder (lazy) or parse (eager)

2. `ImmutableEngine::get()` — K-way merge across all in-memory readers
   - Same algorithm as `Snapshot::get()` (scan all readers, highest LSN wins)

3. `ImmutableEngine::range()` — K-way merge via BinaryHeap
   - Same algorithm as `Snapshot::range()` and `SegmentStore::range_scan()`

4. `ImmutableEngine::prefix()` — range scan with prefix upper bound

5. `ImmutableEngine::with_remote_store(remote, manifest_key)`
   - Downloads manifest from object storage
   - Lazy mode: stores metadata, fetches segments on first access
   - Eager mode: downloads all segments immediately

**Tests:**
- Multi-segment K-way merge: same key in two segments, higher LSN wins
- Lazy fetch: first `get()` triggers download; second `get()` is local
- Error handling: missing segment in remote → `Err`, not panic
- Memory pressure: verify no leaks on repeated open/close

### Wave 3: RemoteStore Integration + Manifest Bundle

1. Extend `RemoteStore` trait with optional sidecar methods:
   ```rust
   fn upload_aux(&self, hash: &[u8; 32], ext: &str, data: &[u8]) -> Result<(), EdgestoreError>;
   fn download_aux(&self, hash: &[u8; 32], ext: &str) -> Result<Vec<u8>, EdgestoreError>;
   ```
   Default implementations return `Err(NotImplemented)` so existing stores compile.

2. `S3RemoteStore` implements `upload_aux`/`download_aux` using the same S3 client, with keys like `segments/{hash_hex}.{ext}`.

3. `FilesystemRemoteStore` implements them as local files.

4. Update `archive_segments()` in `TieredEngine` to optionally upload sidecars:
   - If `upload_sidecars` config is true, upload `.idx`, `.xf`, `.meta` alongside `.dat`
   - This eliminates the one-time decompression cost on `ImmutableEngine` init

5. Manifest generation: add `Engine::export_manifest_json()` that produces the single JSON object format.

**Tests:**
- Sidecar upload/download roundtrip
- ImmutableEngine with pre-built sidecars: zero decompression, just download + parse JSON
- ImmutableEngine without sidecars: derive from `.dat`, verify correctness

## Cross-Cutting Concerns

### Cost Model

| Operation | Cost (per 1K requests) |
|-----------|------------------------|
| Get manifest (1× 50KB) | ~$0.0004 |
| Get segment .dat (16MB) | ~$0.0004 + egress fees |
| ListObjectsV2 (1 page) | ~$0.005 |

Key cost drivers:
- **List API calls** are expensive (paginated scans). The single-manifest design eliminates them entirely.
- **Egress fees** vary by provider ($0.05–$0.09/GB is common). Fetching a 16 MB segment costs ~$0.001 in egress. Fetching 100 segments/day = ~$0.10/day.
- **Ingress** is typically free. Uploading archived segments costs only storage ($0.023/GB/month on standard tiers).
- Some providers offer zero-egress pricing for reads within their network. Evaluate provider-specific pricing before committing.

### Security

- Manifest is public-read or signed-URL only. It contains no sensitive data (just hashes and key bounds).
- Segment files are content-addressed; knowing the hash does not reveal the data unless you can read the object.
- Use bucket policies: public-read for low-sensitivity data, signed URLs for private data.
- ImmutableEngine never writes; even if compromised, the attacker cannot corrupt the remote store.

### Performance Targets

| Metric | Target | Notes |
|--------|--------|-------|
| Cold start (lazy, manifest cached) | <50ms | Download manifest + parse JSON |
| Cold start (lazy, manifest not cached) | <200ms | + one remote round-trip |
| Query latency (cache hit) | <5ms | In-memory segment scan |
| Query latency (lazy fetch, 1 segment) | <100ms | + remote download + decompression |
| Memory per segment | ~16MB raw + ~1MB index/filter | Can stream large segments if needed |
| Max segments in memory | 1000 | ~1.6GB total; configurable |

## Open Questions

1. **Should `ImmutableEngine` live in `edgestore` core or a new crate?**
   - Argument for core: reuses `segment`, `types`, `snapshot` modules already in core
   - Argument for separate crate: keeps core small; serverless users don't need WAL, compaction, or vector search if they only want KV reads
   - **Recommendation:** Start in core as `edgestore::immutable::ImmutableEngine`. Move to separate crate if bundle size becomes an issue.

2. **Vector search and text search in `ImmutableEngine`?**
   - Vectors: `ImmutableEngine` can hold `VectorRecord` data in segments. Search is a full scan (same as flat SIMD). No HNSW (HNSW requires mutable index).
   - Text: `ImmutableEngine` can hold raw text records. Search requires rebuilding the inverted index from segments on init — expensive. **Recommendation:** Defer text search to v2. Start with KV only.

3. **Should the manifest include a Merkle root for integrity?**
   - Yes. The writer computes a Merkle root over all segment hashes. `ImmutableEngine` verifies it on init. Prevents manifest tampering.

4. **Cache eviction strategy?**
   - LRU on segments. Configurable max memory. When limit hit, evict oldest-accessed segment. Re-download on next access.
