<objective>
Implement `vector_search` — a brute-force flat scan over all vector records in a namespace.

1. Scan all keys in synthetic namespace `__vec__{ns}` via `prefix` or `range` on the KV layer.
2. For each key, decode the vector, compute distance to query vector.
3. Maintain top-k results in a min-heap (or max-heap with inverted ordering).
4. Return results sorted by ascending distance.
5. Respect Delete tombstones — deleted vectors are skipped.
6. Validate query dims/dtype match the collection's expected format (or at least are consistent per-call).

The search is brute-force by design for Phase 5. HNSW index is Phase 6 (D12).

Output: edgestore/src/vector/search.rs, updated edgestore/src/engine.rs
</objective>

    - `VectorSearchResult` struct:
      ```rust

      pub struct VectorSearchResult {
          pub key: Vec<u8>,

      }
      ```
    - `vector_search` function signature:
      ```rust
      pub fn vector_search(
          engine: &Engine,
          ns: &[u8],
          query: &VectorRecord,
          k: usize,
          metric: Metric,
      ) -> Result<Vec<VectorSearchResult>, EdgestoreError>
      ```
      - Note: takes `&Engine` not `&mut self` because search is read-only
    - Algorithm:
      1. Validate k > 0; else return empty vec
      2. Build synthetic namespace: `vec_ns = vector_namespace(ns)`
      3. Use `engine.prefix(&vec_ns, b"")` to get all vector records in namespace
         - Wait: prefix needs the prefix bytes, not namespace. We need to get all keys in the namespace.
         - Use `engine.range(&vec_ns, b"\x00", b"\xff\xff\xff\xff")` or similar to get all keys
         - Better: use `engine.prefix(&vec_ns, b"")` if the API supports empty prefix for "all keys in namespace"
         - Check: the Engine::prefix API takes (ns, prefix). To get all keys in the namespace, use prefix="".
      4. For each (key, value) in the results:
         - Skip if the value is a Delete tombstone (value == None or op == Delete)
         - Actually, prefix/range returns (raw_key, value) pairs where value is already filtered for deletes
         - But we need to check: in the current Engine, range/prefix filters out deletes. Good.
         - Decode value bytes to VectorRecord
         - Validate query.dims == candidate.dims and query.dtype == candidate.dtype; else skip or error
         - Compute distance: `distance(&query.data, &candidate.data, query.dtype, metric)`
         - Push into heap
      5. Extract top-k from heap, sort by ascending distance, return
    - Heap strategy:
      - Use `std::collections::BinaryHeap` as a max-heap by inverting ordering
      - Store `(std::cmp::Reverse(distance), key)` so BinaryHeap (max-heap) pops smallest distance
      - Or store `(OrderedFloat(distance), key)` with custom Ord
      - Simpler: use `BinaryHeap<(std::cmp::Reverse<OrderedFloat>, Vec<u8>)>`
      - Even simpler: store `(Reverse<NotNan<f32>>, Vec<u8>)` — NotNan for safe Ord
      - Simplest: just collect all results in a Vec, sort, take k. N is small in tests.
      - For correctness in Phase 5: simple Vec + sort is fine. Optimization is future work.
      - But requirement says 100K vectors p99 < 50ms — we need heap for performance.
      - Use BinaryHeap with Reverse(distance):
        ```rust
        let mut heap: BinaryHeap<(Reverse<OrderedFloat<f32>>, Vec<u8>)> = BinaryHeap::new();
        // Actually OrderedFloat is from ordered-float crate — let's avoid new deps.
        // Use a wrapper struct:
        struct HeapItem(f32, Vec<u8>);
        impl Ord for HeapItem { ... } // compare by f32, treat NaN as large
        ```
      - Or simpler: `BinaryHeap<(Reverse<usize>, Vec<u8>)>` where usize is distance scaled to integer? No, that's lossy.
      - Best: add `ordered-float = "4"` crate, or just use a simple wrapper:
        ```rust
        #[derive(PartialEq)]
        struct HeapItem(f32, Vec<u8>);
        impl Eq for HeapItem {}
        impl Ord for HeapItem {
            fn cmp(&self, other: &Self) -> std::cmp::Ordering {
                self.0.partial_cmp(&other.0).unwrap_or(std::cmp::Ordering::Equal)
            }
        }
        impl PartialOrd for HeapItem {
            fn partial_cmp(&self, other: &Self) -> Option<std::cmp::Ordering> {
                Some(self.cmp(other))
            }
        }
        ```
        Then use `BinaryHeap<HeapItem>` — it pops max, so we want max-distance at top, then replace when we find smaller.
        Actually BinaryHeap is a max-heap by default. So we want the largest distance at the top, and when we find a smaller one, we pop and push.
        Wait: we want to keep the k smallest. So we maintain a max-heap of size k. When we see a new item:
        - If heap size < k: push
        - Else if new_distance < heap.peek().distance: pop, push new
        - This requires heap to be ordered by distance descending (max-heap)
        - BinaryHeap in Rust IS a max-heap, so HeapItem ordered by distance ascending means peek is smallest... wait no.
        - Let's be careful:
          - `BinaryHeap::peek()` returns the MAXIMUM element according to Ord
          - We want `peek()` to return the LARGEST distance among the k items (so we can replace it with a smaller one)
          - So HeapItem::cmp should return `other.0.partial_cmp(&self.0)` (reverse)
          - Then peek() returns the item with largest distance
          - If new_distance < peek_distance: pop, push new
        - Yes, this works.
