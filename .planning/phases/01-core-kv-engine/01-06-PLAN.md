<objective>
Implement crash recovery. When Engine::open is called on an existing database directory, it finds all WAL files, replays their records into the memtable, and restores lsn_counter and txid_counter. Recovery is deterministic: same WAL files always produce the same memtable state. Partial writes at crash time are discarded safely.

Purpose: Without recovery, every process restart loses all data. This plan makes the engine durable — the core promise of Phase 1.

Output: `edgestore/src/recovery.rs` with WAL file scanning and sequential replay. Updated `Engine::open` integrating recovery. Crash recovery unit tests passing.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem→recovery | WAL file bytes and filenames are read from disk — both must be treated as untrusted |
| WAL filename→engine | WAL filenames used to determine replay order — must be validated before use |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Tampering | WAL filename pattern matching | mitigate | list_wal_files validates exact format (24 chars, prefix "wal-", suffix ".log", 16 hex chars in middle); non-matching files silently ignored; no path traversal via filename |
| T-06-02 | Tampering | Path traversal via DB path | mitigate | all WAL paths constructed as `config.path.join(validated_filename)`; join() does not allow absolute or `..` components in the filename portion after the pattern validation check |
| T-06-03 | Tampering | WAL record injection via crafted lsn | mitigate | lsn values from replayed records are used only to update max_lsn counter; they do not control code flow during replay; last-write-wins is by replay order, not by lsn comparison |
| T-06-04 | Denial of Service | Malicious WAL file with huge record count | mitigate | WalReader::read_records processes records one at a time with bounded per-record allocation; no pre-allocation based on untrusted count fields |
| T-06-05 | Repudiation | Recovery skipping corrupt records | accept | Corrupt records are logged (eprintln) and skipped; this is the correct behavior for partial writes; acknowledged writes always have CRC-valid records because fsync preceded acknowledgment |
</threat_model>
