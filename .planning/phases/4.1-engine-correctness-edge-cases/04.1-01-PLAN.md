## Objective

Add inline WAL rotation to `Engine` so that long-running sessions rotate the WAL at the configured `wal_max_bytes` boundary without requiring a reopen. Currently `WalWriter::needs_rotation` is checked only at `Engine::open`; writes in a running session never trigger rotation.

## Context

`WalWriter::needs_rotation(now_secs: u64) -> bool` already exists in `edgestore/src/wal.rs`. The threshold logic is correct. The bug is purely in the callers: `Engine::put`, `Engine::put_with_ttl`, `Engine::delete`, and `Engine::commit_transaction` each call `self.wal.append(...)` but never check rotation afterward.

`next_wal_path(db_path, lsn)` (private fn in `engine.rs`) produces `wal-{lsn:016x}.log`. Rotation simply fsyncs the current WAL file and calls `WalWriter::create` with the next path. Recovery already handles multiple WAL files (see `recovery.rs::recover_from_wal` — iterates all WAL files sorted ascending).

<action>
Add a private method `rotate_wal_if_needed(&mut self) -> Result<(), EdgestoreError>` to `Engine` in `edgestore/src/engine.rs`.

The method body:
1. Compute `now_secs` using `SystemTime::now().duration_since(UNIX_EPOCH).unwrap_or_default().as_secs()`
2. If `!self.wal.needs_rotation(now_secs)` → return `Ok(())`
3. `self.wal.fsync()?;`
4. `let new_path = next_wal_path(&self.config.path, self.lsn_counter);`
5. `self.wal = WalWriter::create(&new_path, &self.config)?;`
6. Return `Ok(())`

Place the method after the `delete` method and before `flush_to_segments`.
</action>

- Method calls `self.wal.fsync()` before `WalWriter::create`

- A long-running engine that writes enough data rotates the WAL without a reopen

</truths>

<threat_model>
Internal correctness fix — no external inputs, no network surface. The only risk is data loss if `rotate_wal_if_needed` creates the new WAL file but the old file was not yet fsynced. Mitigated: `self.wal.fsync()` is called inside `rotate_wal_if_needed` before `WalWriter::create`, ensuring the old WAL is durable before switching.
</threat_model>
