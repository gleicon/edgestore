<objective>
Implement the Transaction API. Transactions buffer WAL records in memory, then commit all of them as a single atomic batch with one fsync. This is the group commit mechanism. Rollback simply discards the buffer.

Purpose: The transaction API is how callers get atomic multi-key writes. Group commit is also the primary durability optimization — without it, every single put would fsync, which is catastrophic for throughput.

Output: `edgestore/src/transaction.rs` with full transaction lifecycle including convenience `tx.commit(engine)` and `tx.rollback(engine)` wrappers. `Engine::begin()` wired. All transaction unit tests passing.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller→Transaction buffer | Caller accumulates records in Transaction before engine sees them |
| Transaction→Engine::commit | Pending buffer crosses from Transaction into WAL/memtable at commit time |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Tampering | Transaction state machine | mitigate | TxState enum prevents double-commit and post-rollback writes; take_pending() returns Err if state != Active |
| T-05-02 | Denial of Service | Unbounded pending buffer in Transaction | accept | v1 single-writer model; no concurrent transactions; very large transactions are caller's responsibility; document max recommended transaction size |
| T-05-03 | Repudiation | txid assignment | mitigate | txid_counter increments monotonically per Engine::begin(); never reused within a single Engine instance; recovery will restore max txid from WAL replay (plan 01-06) |
| T-05-04 | Tampering | fsync skipping on commit | mitigate | `commit_transaction` always calls `self.wal.fsync()` after all appends; no code path in commit skips fsync; enforced by unit test that verifies data persistence |
</threat_model>
