1//! This library implements Xor Filters and their derivatives. Xor filters are data structures for fast approximation of set
2//! membership using little memory. Probabilistic filters like xor filters are useful for
3//! quickly estimating of the existence of an entity to avoid using an expensive resource.
4//! For example, they can be used to [reduce disk writes] in a cache or [identify malicious URLs].
5//!
6//! Xor filters are faster and smaller than Bloom and Cuckoo filters.
7//! Xor filters incur a relative time penalty in construction, but are very fast in lookups; the
8//! expectation is that construction of a filter is amortized after many queries.
9//!
10//! Xor filters operate only on sets of 64-bit (unsigned) integers. This library does not provide
11//! methods for hashing arbitrary types to 64-bit integers. Xor filters are immutable,
12//! serializable, and guarantee no false negatives. This library is `no_std` and [`needs_allocator`].
13//!
14//! Filters are implemented as described in the paper
15//! "[Xor Filters: Faster and Smaller Than Bloom and Cuckoo Filters]", in the upcoming
16//! "Binary Fuse Filters: Fast and Smaller Than Xor Filters", and in Daniel Lemire's [go] and
17//! [c] implementations. All are useful references on the theory behind xor filters. For
18//! performance statistics, refer to individual filters' documentation in this crate or the
19//! mentioned papers.
20//!
21//! ## General considerations for all filters
22//!
23//! It is highly recommended to use the `BinaryFuse` family of xor-like filters. `BinaryFuse`
24//! filters can fail to construct, but almost always only if they are constructed with duplicate
25//! keys. If you need a filter that will unconditionally succeed in construction (up to duplicate
26//! keys), use the `Xor` family of filters.
27//!
28//! For a given `N`, a `BinaryFuseN` and `FuseN` filter are roughly equivalent in size, uniformity
29//! of key distribution, and false-positive rate.
30//!
31//! An `XorN` filter is larger, less uniform, and has a higher false-positive
32//! rate than both a `BinaryFuseN` and `FuseN` filter.
33//!
34//! A `BinaryFuseN` filter's construction is faster, uses less memory, and is more likely to
35//! succeed compared to a `FuseN` filter's construction.
36//!
37//! The false-positive rate of a filter with fingerprint size `N` is around `2^{-N}`; for more
38//! numbers, see the documentation of each individual filter.
39//!
40//! ### Assumed pre-conditions
41//!
42//! - It is a pre-condition that all filters are constructed from a data structure containing no
43//!   duplicate keys. You must perform any de-duplication needed yourself before constructing a
44//!   filter.
45//!
46//! ## FAQ
47//!
48//! ### What's the difference between "Fuse" and "Binary Fuse" filters?
49//!
50//! Fuse filters use a [fuse graph] to reduce the space required to hold fingerprints. Binary Fuse
51//! filters further exploit fuse graphs in a novel manner described in the upcoming
52//! "Binary Fuse Filters: Fast and Smaller Than Xor Filters". In particular, Binary Fuse filters
53//! use a binary-partitioned fuse graph, and are different enough from the "original" Fuse filters
54//! to deserve a unique name.
55//!
56//! [fuse graph]: https://arxiv.org/abs/1907.04749
57//! [reduce disk writes]: https://en.wikipedia.org/wiki/Bloom_filter#Cache_filtering
58//! [identify malicious URLs]: https://en.wikipedia.org/wiki/Bloom_filter#Examples
59//! [`needs_allocator`]: https://doc.rust-lang.org/1.9.0/book/custom-allocators.html
60//! [Xor Filters: Faster and Smaller Than Bloom and Cuckoo Filters]: https://arxiv.org/abs/1912.08258
61//! [go]: https://github.com/FastFilter/xorfilter
62//! [c]: https://github.com/FastFilter/xor_singleheader

115/// Methods common to xor filters.
116pub trait Filter<Type> {
117    /// Returns `true` if the filter probably contains the specified key.
118    ///
119    /// There can never be a false negative, but there is a small possibility of false positives.
120    /// Refer to individual filters' documentation for false positive rates.
121    fn contains(&self, key: &Type) -> bool;
122
123    /// Returns the number of fingerprints in the filter.
124    fn len(&self) -> usize;
125}
126
127/// Equivalent to Filter except represents a reference to fingerprints stored elsewhere.
128pub trait FilterRef<'a, Type>: Filter<Type> {
129    /// The alignment required of the fingerprints slice.
130    const FINGERPRINT_ALIGNMENT: usize;
131
132    /// Create a filter from memory slices. These slices can be mmap from a file. The descriptor
133    /// is eagerly destructured while the fingerprints reference is retained. If the fingerprints
134    /// slice provided doesn't have an alignment of `FINGERPRINT_ALIGNMENT`, this function will
135    /// panic.
136    fn from_dma(descriptor: &[u8], fingerprints: &'a [u8]) -> Self;
137}

139/// DMA serializable filters are ones who can be essentially directly accessed into/out of DMA buffers.
140///
141/// This isn't a true 0-copy implementation and instead we make the following simplification.
142/// A DMA serializable filter has two components - the "fixed" descriptor and the variable length fingerprints.
143/// The fixed descriptor is small (a few words at most) and is copied into / out of the serialized form.
144/// The variable length fingerprints however are referenced directly.
145pub trait DmaSerializable {
146    /// The serialized length of the descriptor. Very small and safe to allocate on-stack if needed.
147    const DESCRIPTOR_LEN: usize;
148
149    /// Copies the small fixed-length descriptor part of the filter to an output buffer.
150    fn dma_copy_descriptor_to(&self, out: &mut [u8]);
151
152    /// Obtains the raw byte slice of the fingerprints to serialize to disk.
153    fn dma_fingerprints(&self) -> &[u8];
154}
